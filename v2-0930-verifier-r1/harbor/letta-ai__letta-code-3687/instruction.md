MessageChannel availability and execution should be owned by the channel gateway/controller, not inferred locally from channel adapter state or propagated through subagent/runtime execution context.

When a channel route is active for a conversation, ChannelGateway must register the `MessageChannel` external tool for that runtime/conversation. Tool discovery for process-owned turns should then find and expose this registered external tool by runtime context, including when the tool is not scoped to a particular listener connection. The generated `MessageChannel` tool should include the compact channel-specific guidance used for Slack-style requests, and its JSON schema must include a `target` property.

Channel request envelopes sent to the model should no longer rely on registering a running `ChannelAdapter` in `ChannelRegistry` or passing `channelToolScope` into `prepareToolExecutionContextForModel`. Instead, tests and callers should be able to register the gateway-built external tool for a runtime such as `{ agentId: "agent-1", conversationId: "conv-slack" }`, call `prepareToolExecutionContextForModel(..., { clientToolAllowlist: ["MessageChannel"], runtimeContext: { agentId: "agent-1", conversationId: "conv-slack" } })`, and see `MessageChannel` in the prepared tool set.

Runtime external tool execution must route process-owned tool calls back through the controller that registered the tool, even when the runtime context only contains `agentId` and `conversationId` and no `connectionId`.

Channel context should not be serialized into subagent child process environments. `composeSubagentChildEnv` should not emit an inherited channel context environment variable, and subagent launch should not add `MessageChannel` as an extra tool simply because the parent had channel context. Channel turn sources should be tracked by the gateway for the active/routed runtime instead.

The websocket `runtime_start` command needs to support a boolean `preserve_skill_sources` field. `isRuntimeStartCommand` should accept `preserve_skill_sources: true` or `false` and reject non-boolean values such as `"yes"`. When handling `runtime_start`, if `skill_sources` is omitted and `preserve_skill_sources` is not true, existing skill source overrides for that scoped runtime should be cleared as before. If `preserve_skill_sources: true` is provided and `skill_sources` is omitted, the existing `skillSources` and `skillSourcesByConversation` entry must remain unchanged. This is needed so a subsequent runtime start used only to update external tools does not accidentally erase previously configured skill sources.

Attached App Server connections must not start process-owned services or bypass the listener startup barrier. `startAppServer`/listener attachment should allow disabling process service startup for attached clients, while the primary listener startup remains responsible for starting process services only after its startup path, including gateway startup, is complete.
