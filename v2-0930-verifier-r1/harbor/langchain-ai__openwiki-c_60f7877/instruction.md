The refactor branch is missing current main behavior for OpenWiki’s native wiki visualizer and the expanded telemetry error taxonomy.

Add a new `openwiki visualize` CLI command that serves a generated wiki directory as a local, interactive visualizer. By default it should visualize `./openwiki`, bind only to `127.0.0.1`, use port `4321`, increment to the next available port on conflicts, and open the default browser unless `--no-open` is passed. It should also accept an explicit wiki directory path and `--port <port>`. If the wiki directory does not exist, fail with a friendly error like `Wiki directory not found: <path>. Run \`openwiki --init\` first, or pass a path.` The server should expose only fixed routes for the app shell, client assets, graph JSON, and live reload events; unknown paths, including traversal-style URLs such as `/..%2f..%2fetc%2fpasswd`, must return `404 Not found` and must not be mapped to the filesystem. The visualizer should watch the wiki directory and notify connected clients when markdown files change.

Implement the graph-building API used by the visualizer in `src/visualize/graph.ts`. It should export `splitFrontmatter`, `firstHeading`, and `buildGraph`. `splitFrontmatter` must parse simple YAML-style markdown frontmatter delimited by `---`, including scalar values, quoted scalar values, inline arrays such as `tags: [alpha, beta]`, and dashed lists such as `authors:\n  - Ada\n  - Grace`; when no frontmatter exists it should return an empty metadata object and the original body. `firstHeading` should return the first markdown H1 text or `undefined`. `buildGraph(wikiRoot)` should recursively collect markdown pages under the wiki root, excluding scaffolding files such as `INSTRUCTIONS.md`, derive stable node ids from relative markdown paths without the `.md` extension, title the root `index.md` node as `Home`, otherwise prefer frontmatter `title` and then the first H1 heading, resolve markdown links between existing pages into directed `{ source, target }` edges, ignore links to missing pages and self-links, record backlinks on target nodes, and avoid following symlinks that escape the wiki root.

Update the telemetry error classification APIs to use the newer taxonomy. `classifyError(error)` should no longer return a raw string; it should return a sanitized object with `errorClass` and, when applicable, `errorDetail`. It must never include raw exception messages, paths, tokens, or other secret-bearing details. Expected classifications include: `AbortError` or “aborted” as `{ errorClass: "aborted" }`; HTTP 401/403 as `{ errorClass: "provider_error", errorDetail: "auth" }`; 429 as `{ errorClass: "provider_error", errorDetail: "rate_limit" }`; 500 as `{ errorClass: "provider_error", errorDetail: "server_error" }`; 503 and 529 as `{ errorClass: "provider_error", errorDetail: "overloaded" }`; nested `response.status` should be recognized the same way as top-level `status` or `statusCode`; provider context-length codes or messages should classify as `{ errorClass: "context_limit_error" }`; content-policy/content-filter messages should classify as `{ errorClass: "provider_error", errorDetail: "content_filter" }`; missing API keys should classify as `{ errorClass: "config_error", errorDetail: "missing_credentials" }`; missing base URL/config should classify as `{ errorClass: "config_error", errorDetail: "missing_base_url" }`; invalid model messages should classify as `{ errorClass: "config_error", errorDetail: "invalid_model" }`; timeout messages should classify as `{ errorClass: "provider_error", errorDetail: "timeout" }`; network failures should classify as `network_error` with details such as `dns`, `refused`, or `unreachable` when detectable; filesystem errors such as `ENOENT` should classify as `{ errorClass: "filesystem_error", errorDetail: "not_found" }`; otherwise fall back to `{ errorClass: "agent_error" }`.

Also expose the telemetry helpers expected by callers and tests: `describeErrorForTelemetry`, `tagErrorStage`, `inStage`, and `inStageSync` from `src/telemetry/errors.ts`; taxonomy helpers such as `deriveOwner` and `normalizeErrorDetail` from `src/telemetry/taxonomy.ts`; and `buildRunEvent` from `src/telemetry/senders.ts`. Run telemetry events should include the new error class/detail/stage/owner fields consistently while preserving existing telemetry gates such as `OPENWIKI_TELEMETRY_DISABLED`, CI suppression, and tee-file behavior.

Additional visualization and CLI contracts covered by the tests: expose the visualization client helpers from `src/visualize-client-lib.ts`, including deterministic node/link color selection, node radius calculation, HTML escaping, graph rendering signatures, and any helper exports used by the client-library tests. The visualize command should accept both `--port <port>` and `--port=<port>` forms, reject ports outside `1024..65535` with the expected validation error, and continue to serve only safe loopback paths. Telemetry run events should include the sanitized `app_version` field in addition to the error taxonomy fields described above.
