Random behavior in Tetrad is currently inconsistent because many code paths instantiate and pass around `java.util.Random` directly, often with local seeds, while other parts of the project use `edu.cmu.tetrad.util.RandomUtil`. This makes simulations, graph generation, GUI randomization actions, bootstrap/shuffle sampling, permutation-based tests, and other stochastic algorithms difficult to control consistently from the project-wide random seed and leads to non-reproducible or mismatched results across runs.

Update the codebase so stochastic behavior uses `RandomUtil` as the common source of randomness instead of constructing independent `Random` instances or exposing `Random` parameters in public/internal APIs where the project-wide random utility should be used. Affected behavior includes hybrid conditional Gaussian model randomization and sampling, GUI randomization in `HybridCgImEditor` and related wrappers, data subset sampling modes such as shuffle, subsample, and bootstrap, random graph/MIM generation, KCI permutation/random data generation, SEM and simulation utilities, statistical test helpers, and similar random draws throughout the library and GUI.

APIs that currently require callers to provide a `Random` solely for sampling or random initialization should instead support using the shared random utility directly. For example, `HybridCgIm.sample(...)` and helper methods for constructing random `HybridCgIm` instances should be usable without passing a `java.util.Random`, and their random draws should come from `RandomUtil`. GUI controls or parameters that only exist to seed a local `Random`, such as the seed field in the unmixing parameter editor, should not present or rely on a separate local RNG seed when randomization is governed globally.

All common random operations should have `RandomUtil` equivalents and use them consistently, including uniform doubles, bounded integers, Gaussian draws, uniform ranges, shuffling lists, random permutations, and any discrete sampling needed by existing algorithms. Randomized algorithms should continue to produce valid results: probability rows must still normalize to 1, variances must remain positive and in their intended ranges, bootstrap samples must draw with replacement from the selected rows, shuffle/subsample must return valid reordered or truncated row selections, and permutation-based procedures must still produce p-values in valid ranges.

Because the underlying random stream changes when replacing local `Random` instances with `RandomUtil`, tests and deterministic expectations that depend on exact random draws may need to be updated to the new reproducible outputs. The goal is not to preserve the exact sequences produced by `java.util.Random`, but to ensure that all random behavior is centralized, reproducible through `RandomUtil`, and functionally equivalent with respect to model validity and algorithm behavior.

Additional deterministic-test requirement: after centralizing stochastic behavior on `RandomUtil`, update the affected tests and code paths to use the resulting `RandomUtil` stream consistently. Deterministic assertions that depend on random draws should match the new reproducible `RandomUtil` outputs, including the exact sequences observed by the updated hybrid model, sampling, graph generation, KCI, SEM, simulation, and statistical helper tests.
