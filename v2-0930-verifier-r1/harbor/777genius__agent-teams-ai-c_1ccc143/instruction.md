The task change review flow has several correctness gaps that need to be addressed.

`ChangeExtractorService.getTaskChanges(teamName, taskId, options)` currently caches detailed task change results too broadly. Requests for the same `teamName` and `taskId` but different scope inputs such as `owner`, `status`, `intervals`, `since`, or `summaryOnly` can reuse stale results from a previous request. For example, if a request for task `1` with `owner: "bob"` finds no logs, a later request for the same task with `owner: "alice"` may incorrectly return the cached empty result even though Alice has changes. The cache must distinguish task-change results by all scope-defining request options that affect log discovery and extraction.

The same service also mishandles fallback aggregation for equivalent Windows paths written with different separators or drive-letter casing. When logs contain changes for paths such as `C:\repo\src\same.ts` and `C:/repo/src/same.ts`, they should be treated as the same file. The resulting `TaskChangeSetV2.files` should contain a single `FileChangeSummary`, with the relative path resolved consistently against the configured project path, e.g. `src/same.ts`, and line counts combined across snippets.

`TaskBoundaryParser` should recognize both camelCase and snake_case task identifiers in tool inputs. `TaskUpdate` entries and MCP task marker tools such as `task_start`, `task_complete`, and `task_set_status` may provide the task id as either `taskId` or `task_id`, and numeric ids should still be accepted by converting them to strings. A JSONL log using `input: { task_id: "task-123", status: "in_progress" }` must produce the same boundary/scoping behavior as one using `taskId`.

Task-change requests in the renderer should carry the same scope context used by the backend. Helpers should be available to build canonical task-change options from a task object, including `owner`, `status`, `workIntervals` as `intervals`, and a `since` timestamp derived from the earliest known task timestamp. The earliest timestamp should be selected from `createdAt`, work interval `startedAt` values, and history event timestamps, then shifted backward by a two-minute grace window. Presence-cache keys for “task has changes” must include the scope signature, so two requests for the same `teamName` and `taskId` but different owners, intervals, statuses, or `since` values do not collide.

The renderer change-review store should also avoid applying stale asynchronous task-change responses. If `fetchTaskChanges` is called for one task and then called again for another task before the first request resolves, the later request should win. When the earlier response eventually resolves, it must not overwrite `activeChangeSet`, `selectedReviewFilePath`, loading state, or the task-change presence cache for the current request.

The lightweight `checkTaskHasChanges` path should request summary-only task changes, use the scoped presence-cache key, avoid duplicate in-flight checks for the same scoped request, cache negative results only for the intended TTL, and allow immediate retry after transient API errors instead of storing an error as a negative result.

Plugin catalog items need to expose their origin. The shared `PluginCatalogItem` type and catalog data returned by `PluginCatalogService` should include a `source` field. Official marketplace plugins should be emitted with `source: "official"` so renderer extension state and UI code can display and preserve source information.

Generated Claude MCP configuration should not discard existing user MCP servers. When `TeamMcpConfigBuilder.writeConfigFile()` creates the temporary config containing the generated `agent-teams` MCP server, it should also read the user-level Claude config file `.claude.json` from the home directory, preserve valid entries under its `mcpServers` object, and merge them into the generated config. The generated `agent-teams` server should remain present and take precedence for its own server name, while missing, malformed, or unreadable user config files should not prevent config generation.
