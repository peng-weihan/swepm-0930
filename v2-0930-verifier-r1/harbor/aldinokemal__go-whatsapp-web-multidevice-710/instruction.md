Chatwoot integration needs to support per-device and multi-inbox routing instead of relying only on the global `CHATWOOT_*` environment variables. The current single global Chatwoot configuration can misroute messages when multiple WhatsApp devices, Chatwoot inboxes, accounts, or servers are used. A device should be able to have its own Chatwoot URL, account ID, inbox ID, API token, enabled flag, and webhook URL, and both forward and reverse message flows must resolve the correct device/config deterministically.

Add persistent per-device Chatwoot configuration storage and CRUD behavior. A `ChatwootDeviceConfig` should include at least `device_id`, optional `device_jid`, `chatwoot_url`, `account_id`, `inbox_id`, `api_token`, `enabled`, timestamps, and an internal ID. Repository operations must support create/update/delete, list/count, lookup by `device_id`, lookup by either `device_id` or `device_jid`, and lookup by `(account_id, inbox_id)` only when that mapping is unambiguous. If one row’s `device_id` equals another row’s `device_jid`, identifier lookup must return an explicit ambiguity error rather than picking an arbitrary row. A row where its own `device_id` and `device_jid` are the same is not ambiguous.

Expose authenticated REST endpoints for managing these configs: `GET /chatwoot/configs`, `GET /devices/:device_id/chatwoot/config`, `PUT /devices/:device_id/chatwoot/config`, and `DELETE /devices/:device_id/chatwoot/config`. The `:device_id` parameter may be either the user-facing device ID or the WhatsApp JID and should resolve consistently across GET, PUT, and DELETE. Read responses must mask `api_token`, showing only the last four characters, and include a `webhook_url` for the device. `PUT` must require `chatwoot_url`, positive `account_id`, positive `inbox_id`, and an `api_token` on create. On update, an omitted/empty `api_token`, or the masked token value returned by a previous GET, must keep the stored token rather than storing the mask as the credential. The `enabled` field should default to true on create and preserve the existing value when omitted on update. `DELETE` must remove the device config and any Chatwoot message links scoped to that config, so stale conversation links cannot affect a later delete-and-recreate rebind.

The REST API must reject unsafe Chatwoot URLs. `chatwoot_url` should be canonicalized and validated so only `http` and `https` URLs are accepted, embedded credentials/userinfo are rejected, and hosts that resolve to private, loopback, link-local, or metadata IP addresses are rejected to prevent SSRF. `CHATWOOT_ALLOWED_HOSTS` should be supported as an explicit host allowlist/trust escape hatch where applicable.

Once at least one per-device config exists, the system must stop falling back to the global `CHATWOOT_*` environment config for unmapped devices or conversations. In this per-device mode, an unmapped forward should be skipped/fail fast instead of being sent to the env-configured inbox, and an unmapped reverse webhook payload should be acknowledged but not delivered through a default WhatsApp device. The legacy env fallback remains valid only when the per-device config table is empty.

Forwarding WhatsApp messages to Chatwoot must resolve the correct per-device client using the device ID or JID. Message links created from live forwarding, retries, read receipts, hard deletes, history sync, or imports must be scoped with the Chatwoot account/config where appropriate so reverse routing cannot cross accounts, configs, or servers. The sent-message echo/dedup cache must be partitioned by Chatwoot account as well as message ID so identical numeric message IDs in different Chatwoot accounts do not suppress each other.

Add a per-device webhook endpoint `POST /chatwoot/webhook/:device_id`. This endpoint should validate the optional shared webhook secret and, for message events, ensure the payload’s Chatwoot account and inbox match the stored config for that device; mismatches should return 401. Unknown device IDs and non-message events should be acknowledged with 200 and ignored rather than causing unauthorized errors or polluting caches. The existing shared webhook route must also avoid misrouting: reverse resolution should prefer account/config-scoped conversation links, then valid contact attributes, then unambiguous inbox/account mappings, and should use the env fallback only in legacy mode when there are no per-device configs. Contact attribute overrides such as `gowa_device_id` must only be honored in per-device mode when they match the payload’s account and inbox.

Conversation link lookup must be account scoped. Existing legacy links with `chatwoot_account_id = 0` must not act as wildcards in per-device mode, because Chatwoot conversation IDs can collide across accounts. Legacy-zero matching is only acceptable in legacy/env mode. Per-device webhook routing must also scope lookup by config ID so identical `(conversation_id, account_id)` values on different Chatwoot servers cannot steal replies.

Initialize the Chatwoot client registry before any retry worker or WhatsApp event pipeline can attempt forwarding. If the registry is unavailable, live forwarding should log the wiring/configuration problem without enqueuing retry work, and retry jobs should survive/reschedule rather than being marked done and deleted. Registry invalidation must evict cached env-fallback entries as well as per-device entries so creating the first per-device config immediately stops previously cached env fallback behavior.

Per-device sync services must be keyed by the resolved Chatwoot config/client identity. Updating a config, including rotating the token or changing routing details where allowed, must invalidate or rebuild the cached sync service so subsequent sync operations use the new client. If a sync service is rebuilt while a sync is in progress, existing progress state should remain visible and continue to prevent a concurrent duplicate sync. Direct PostgreSQL history import via `CHATWOOT_IMPORT_DB_URI` is supported only in legacy/env mode; per-device configs should use the REST import path.

When a device connects or re-pairs, its WhatsApp JID should be stamped onto its existing per-device config so configs created before pairing can later be found by JID-based forwarding. Any strings derived from Fiber request parameters or request bodies that are retained beyond the request lifetime, such as device IDs used as config keys, registry keys, or sync progress keys, must be copied so they cannot be mutated when the underlying request buffer is reused.

Document the new per-device/multi-inbox Chatwoot behavior, REST endpoints, per-device webhook URL, token masking, SSRF restrictions, `CHATWOOT_ALLOWED_HOSTS`, legacy env fallback rules, edit guard, and the known limitation that agent-initiated conversations cannot be disambiguated from payload alone when separate Chatwoot servers share the same account and inbox IDs unless the per-device webhook URL is used. Update the OpenAPI specification to include the new endpoints and response/error semantics, including `CONFIG_NOT_FOUND`, `INVALID_CHATWOOT_URL`, `INVALID_REQUEST`, and `CONFIG_HAS_LINKED_CONVERSATIONS`.
