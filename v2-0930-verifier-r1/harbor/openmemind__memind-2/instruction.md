The memory store API should be simplified and extended so callers can delete specific stored records while keeping vector storage and retrieval caches consistent.

The public `Memory` API must expose deletion operations for individual memory items and insights: `Mono<Void> deleteItems(MemoryId memoryId, Collection<Long> itemIds)` and `Mono<Void> deleteInsights(MemoryId memoryId, Collection<Long> insightIds)`. Calling `deleteItems` should delete only the requested item ids for the given `MemoryId`. Before removing item rows from the `MemoryStore`, it must look up the requested items with `MemoryStore.getItemsByIds`, collect any non-null `MemoryItem.vectorId()` values, and delete those vectors via `MemoryVector.deleteBatch(memoryId, vectorIds)`. If none of the items have vector ids, vector deletion should be skipped. After item deletion, the retriever must be notified with `MemoryRetriever.onDataChanged(memoryId)`. Calling `deleteInsights` should delete only the requested insight ids through the store and then notify the retriever in the same way; it should not interact with the vector store. Empty id collections should complete without doing work.

The default `Memory` auto-configuration must be able to wire this behavior. The default `Memory` bean now depends on a `MemoryVector` bean in addition to the existing extractor, retriever, store, and tool stats dependencies. If no `MemoryVector` bean is available, default `Memory` creation should fail with a startup error mentioning `MemoryVector`.

The `MemoryStore` abstraction should be refactored around batch-oriented operations and clearer naming. Item persistence should support upserting multiple items and deleting multiple item ids. Insight persistence should support upserting multiple insights, listing insights, querying insights by type and tier, and deleting multiple insight ids. Insight type persistence should be global rather than scoped to a `MemoryId`: `MemoryInsightType` should no longer carry a `memoryId`, default insight types should be created without one, and store APIs for insight types should operate without a `MemoryId`, including getting an insight type by name, listing all insight types, and upserting default insight types.

All in-memory and MyBatis-backed store implementations, converters, initializers, extraction/insight pipeline code, tracing tests, and related call sites should use the refactored store API names and semantics. Default taxonomy seeding should upsert the global default insight types directly, rather than saving them under a synthetic system memory id.
