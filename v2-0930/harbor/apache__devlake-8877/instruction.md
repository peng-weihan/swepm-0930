DevLake needs a new Rootly data source plugin that can be configured, tested, scoped to Rootly services, and used in blueprint v2.0 pipelines to collect Rootly services and incidents into the ticket domain model for DORA/incident metrics.

The plugin should expose the standard data source connection APIs under `/plugins/rootly`, including creating, listing, retrieving, patching, deleting, and testing connections. A Rootly connection must support bearer-token authentication and REST connection settings such as endpoint, proxy, and rate limit. The default Rootly cloud endpoint should include the API version prefix expected by Rootly, `/v1/`. Testing a connection must validate the token against Rootly’s actual current-user endpoint, `GET /users/me`; invalid credentials should surface as a bad-request-style test connection failure, including the unauthorized case.

The plugin must support remote scope discovery and scope configuration for Rootly services. Remote service listing/search should consume Rootly’s JSON:API response shape and page-based pagination. Pagination should not silently stop when optional response metadata such as `meta.current_page` is absent; it should continue based on the requested page and Rootly’s pagination response. Scope CRUD, scope sync state, and blueprint v2.0 APIs must be available. A blueprint v2.0 plan for selected Rootly service scopes should create Rootly tasks with `ConnectionId` and `ServiceId`, and should return ticket board scopes for scopes whose entities include the ticket domain.

The Rootly pipeline must collect and convert services. The service collector should fetch the scoped service with `GET /services/{id}`, unwrap the JSON:API envelope, and persist it to `_tool_rootly_services`. The service converter should create one `ticket.Board` per Rootly service using DevLake’s standard domain ID generation.

The Rootly pipeline must collect, extract, and convert incidents. Incident collection must request Rootly incidents scoped by service UUID using the query parameter `filter[service_ids]=<service id>`, not `filter[services]`, because Rootly’s `filter[services]` matches service names and returns no incidents when given a UUID. The request should also include page parameters such as `page[size]` and `page[number]`, sort by `-updated_at`, and support incremental collection with `filter[updated_at][gt]` when a since timestamp is available. Pagination should be robust and bounded so a malformed response cannot loop forever.

Incident extraction must match Rootly’s real JSON:API incident response format. Incident rows come from resources with top-level `id` and `type`, an `attributes` object, and a sibling `relationships` object. Service membership is found in `relationships.services.data[]` as JSON:API id/type references. If an incident explicitly references services and none match the currently scoped service, the extractor should skip it. If service relationships are omitted or empty, the incident may still be accepted for the current scoped service.

Role-bearing users and severity are nested JSON:API envelopes inside incident attributes. User fields include `user`, `started_by`, `mitigated_by`, `resolved_by`, and `closed_by`, each shaped like `{"data":{"id":"...","type":"users","attributes":{...}}}`. The extracted incident should store role-specific user IDs for creator/user, started-by, mitigated-by, resolved-by, and closed-by. The extractor should emit deduplicated `_tool_rootly_users` rows for inline users found on an incident, preferring `full_name` over `name` over `email` for the user name, and should avoid emitting empty user rows that have neither a name nor an email. Missing required incident timestamps such as `started_at` should produce an extraction error, while a missing `sequential_id` should not fail extraction and should result in incident number `0`.

The Rootly incident model should reflect Rootly’s lifecycle-role model rather than PagerDuty-style assignment lists. There should not be an assignment table, and incidents should not include an urgency field because Rootly incident resources do not provide one. Archived migration models must create schemas compatible with the live models, including helper-provided fields such as connection endpoint/proxy/rate limit, service scope config ID, scope config connection ID/name, indexes such as service ID, and without stale fields such as user URL or incident urgency. A fresh migration should create tables that the live Rootly models can read and write without MySQL “Unknown column” errors.

Incident conversion must create DevLake ticket-domain rows. Each Rootly incident should become a `ticket.Issue` with type `INCIDENT`, status, priority/severity, lead time, and resolution date derived from Rootly fields. It should create one `ticket.IssueAssignee` per distinct role user across creator/user, started-by, mitigated-by, resolved-by, and closed-by, and one `ticket.BoardIssue` linking the incident to its service board. Known Rootly statuses should map to DevLake issue statuses; unknown statuses should not panic and should instead fall back to `IN_PROGRESS` while preserving/logging the original status. Severity mapping should accept case-insensitive `sev0` through `sev4`, while unknown severities should be preserved as-is. Lead time calculation should not produce wraparound values when timestamps are anomalous, such as a resolved time earlier than the started time; in that case lead time should be nil.

The Rootly plugin must be registered with the backend plugin startup path and table-info checks so it loads like other plugins. It should also be registered in the config UI plugin list with an appropriate icon and beta flag so users can create Rootly connections, browse service scopes, and run blueprints from the UI. A Rootly Grafana dashboard should be included for incident metrics using Rootly-backed ticket boards.

Additional implementation contracts covered by the tests: the Rootly incident task package should expose the package-level helpers `buildIncidentsQuery`, `extractRootlyIncident`, `mapStatus`, `mapSeverityToPriority`, `computeLeadTime`, and `issueKeyFor`. `buildIncidentsQuery` should build the expected Rootly incidents endpoint query from the connection and scope options. `extractRootlyIncident` should implement the incident/user extraction rules described above. Status mapping should convert known Rootly lifecycle statuses into DevLake ticket statuses and fall back to `IN_PROGRESS` for unknown values. Severity mapping should handle `sev0` through `sev4` case-insensitively and preserve unknown severities. `computeLeadTime` should return nil for missing or anomalous timestamps, and `issueKeyFor` should fall back to the Rootly incident ID when `sequential_id` is absent, zero, or negative.
