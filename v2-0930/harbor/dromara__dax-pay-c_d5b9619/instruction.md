The platform permission annotations currently use string literals directly in `@PermCode` declarations, such as `menuCode = "system:protocol"` and `code = "view"`. This makes permission codes easy to drift from the frontend permission-code domain structure and prevents compile-time checking of shared permission values.

Add a centralized `cn.daxpay.open.platform.core.code.PermCodes` API in `daxpay-platform-core` that exposes compile-time constants for permission menu codes and action codes, organized as nested interfaces by domain. Controllers should be able to reference these constants directly from annotation attributes, for example `@PermCode(menuCode = PermCodes.System.Protocol.MENU)` and `@PermCode(code = PermCodes.Action.VIEW, nameCn = "查看", nameEn = "View")`.

The constants must be valid Java annotation attribute values, so they need to be compile-time constant strings. Existing permission string values must not change: permission resolution utilities such as `PermCodeUtil.resolveFullCode` should continue to produce the same full permission codes as before when annotations use the new constants. For example, a method annotated with `@PermCode(code = PermCodes.Action.VIEW, nameCn = "查看", nameEn = "View")` and no class-level menu code should still resolve to the action code `view`.

Update controller `@PermCode` usages across the platform and channel modules to use `PermCodes` constants instead of duplicated literals for known menu codes and common action codes. Common actions include values such as `view`, `manage`, `publish`, `update`, `status`, `sign`, `kickout`, `reset_password`, `assign_role`, `resend`, and `test`. The nested menu-code constants should align with the existing permission domains used by the frontend, including channel, merchant, payment, IAM, system, develop, and device domains. Existing Chinese and English permission names should remain unchanged, except where shared name constants are provided for repeated channel merchant view/manage names.
