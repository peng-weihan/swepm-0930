The `@kubb/adapter-oas` parser currently relies on several separate `$ref` resolution paths, some of which mutate the parsed OpenAPI document in place. This makes operation parsing order-dependent and causes referenced path items or request bodies to be read incorrectly when the earlier mutation did not happen.

When a path entry is a `$ref` to a component path item, operation parsing should behave as if the referenced path item were present inline. Path-level parameters from the referenced path item must be merged into the operation parameters, including referenced parameters such as `#/components/parameters/LimitParam`. If an operation does not define its own summary or description, it should fall back to the `summary` and `description` on the referenced path item.

Referenced request bodies must also be resolved consistently. For an operation whose `requestBody` is `{ "$ref": "#/components/requestBodies/CreateThingBody" }`, the resulting operation node should include the referenced request body’s `description`, `required`, and content entries. This must work both when no adapter `contentType` option is set and when a global `contentType`, such as `'application/json'`, is configured. In the broken behavior, setting `contentType` bypasses the code path that used to mutate `operation.schema.requestBody`, so `requestBody.description` and `requestBody.required` are silently returned as `undefined`.

The parser should not depend on mutating the source OpenAPI document to make later reads see resolved `$ref` values. Repeated reads of path items, parameters, request bodies, responses, schemas, and operations should resolve references consistently without changing the original parsed document.

Generated AST output for existing schemas and operations should remain unchanged except for the request body metadata bug described above. Discriminator behavior must remain the same: inline discriminator preservation should still create a required enum property for the discriminator value, and propagated discriminator handling should still patch child schema nodes as before. Shared schema node metadata such as `name`, `nullable`, `title`, `description`, `deprecated`, `readOnly`, `writeOnly`, `default`, `examples`, and `format` must continue to be preserved on emitted schema nodes.
