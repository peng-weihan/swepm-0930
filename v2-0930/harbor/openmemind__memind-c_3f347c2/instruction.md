Memory build configuration needs to be reorganized so extraction and retrieval defaults are expressed through grouped option objects and are actually used by `DefaultMemory` when callers do not pass an explicit config.

`MemoryBuildOptions` should expose nested extraction and retrieval options instead of the previous flat build options. The default options must be reachable through APIs such as `MemoryBuildOptions.defaults().extraction().rawdata().commitDetection()` and `MemoryBuildOptions.defaults().extraction().insight().build()`. The builder should accept a complete `ExtractionOptions` and `RetrievalOptions` object, and `Memory.builder().options(configuredOptions).build()` must propagate the configured `MemoryBuildOptions` into the resulting `DefaultMemory`.

Extraction options should include common extraction settings, raw-data extraction settings, item extraction settings, and insight extraction settings. The raw-data extraction options must contain the conversation chunking configuration and commit detection configuration, preserving `CommitDetectorConfig.defaults()` as the default commit detection value. Existing behavior that previously configured commit detection or insight build options directly on `MemoryBuildOptions` should be represented through the nested extraction options.

Retrieval options should be grouped into common, simple, deep, and advanced retrieval settings. Simple retrieval defaults should include timeout, insight topK, item topK, raw-data topK, and keyword-search enablement. Deep retrieval defaults should include timeout, insight topK, item topK, raw-data enablement/topK, query expansion options, and sufficiency options. Common retrieval options should include cache enablement. Advanced retrieval options should include rerank and scoring configuration.

`DefaultMemory` currently falls back to hardcoded `ExtractionConfig.defaults()` and `RetrievalRequest.of(...)` behavior for methods like `extract(...)`, `addMessage(...)`, `commit(...)`, `retrieve(memoryId, query, strategy)`, and `getContext(...)`. These default calls should instead be derived from the `MemoryBuildOptions` supplied when the memory instance was built. For example, if `MemoryBuildOptions` configures simple retrieval with `Duration.ofSeconds(15)`, item topK `9`, and cache disabled, then `getContext(ContextRequest.of(memoryId, ...))` should invoke the retriever with a `RetrievalRequest` whose `config().timeout()` is 15 seconds, whose `config().tier2().topK()` is 9, and whose cache is disabled. Similarly, if extraction options configure a default scope such as `MemoryScope.AGENT`, a timeout, language, insight enablement, or item foresight enablement, then `commit(memoryId)` and other extraction methods without an explicit `ExtractionConfig` should pass those configured values to the extraction pipeline.

The default deep retrieval configuration should continue to produce a deep strategy with tier1 and tier2 enabled, tier3 disabled, a 120 second timeout, rerank enabled by default, and query expansion defaulting to `maxExpandedQueries == 3`. `DeepStrategyConfig.QueryExpansionConfig` should only expose the number of expanded queries needed by the public tests, with defaults preserving `maxExpandedQueries` as 3 and allowing callers to construct a config such as `new DeepStrategyConfig.QueryExpansionConfig(5)`.

Existing public examples and builder usage should be updated to compile against the grouped option structure, including constructing nested `ExtractionOptions` when customizing insight build settings and nested raw-data options when customizing commit detection.
