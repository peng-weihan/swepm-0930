Provider request construction is currently owned by many individual provider packages through per-provider `request.py` modules, even when the behavior is common to an entire transport family. This makes the provider boundary unclear and causes shared request-policy behavior for OpenAI-compatible chat providers and native Anthropic Messages providers to be duplicated across concrete providers.

Refactor request-policy ownership so shared request-building behavior lives under the transport family packages instead of individual provider packages. OpenAI-compatible chat request policy should be exposed from `providers.transports.openai_chat`, and native Anthropic Messages request policy should be exposed from `providers.transports.anthropic_messages`. There should be no remaining `providers/*/request.py` modules for concrete providers such as Cerebras, DeepSeek, Fireworks, Gemini, Groq, Kimi, Mistral, NVIDIA NIM, OpenCode, OpenRouter, or Z.ai, and neither provider code nor tests should import those old modules.

The refactor must preserve existing observable request-building behavior. OpenAI-chat providers must still convert Anthropic requests with `core.anthropic.build_base_request_body`, map thinking history according to the provider’s thinking setting, convert OpenAI conversion failures into `providers.exceptions.InvalidRequestError`, handle provider-specific `extra_body` support, normalize token fields such as `max_tokens` versus `max_completion_tokens`, optionally strip message `name` fields, remove unsupported body keys, and apply provider-specific post-processing quirks. For example, Cerebras must continue to preserve message `name` fields while remapping `max_tokens` to `max_completion_tokens`, and if `max_completion_tokens` is already present it must take precedence over `max_tokens`.

Native Anthropic Messages providers must still build Anthropic-compatible request bodies with the standard default max-token behavior, thinking payload handling, stream flags, and provider-specific `extra_body` policy. OpenRouter must continue to reject `extra_body` attempts to override reserved fields such as `model`, allow OpenRouter-specific keys such as `transforms` and `plugins`, and use `config.constants.ANTHROPIC_DEFAULT_MAX_OUTPUT_TOKENS` as its default `max_tokens`. Z.ai must continue to reject any request `extra_body` with the error message `Z.ai native Messages API does not support extra_body on requests.`

Provider-specific quirks that are not shared transport-family policy should remain in appropriately named provider modules rather than in generic request modules. Existing public/test-visible helpers should remain importable from their new locations, including Gemini’s `GEMINI_SKIP_THOUGHT_SIGNATURE_VALIDATOR`, NVIDIA NIM’s `NIM_TOOL_ARGUMENT_ALIASES_KEY`, `body_without_nim_tool_argument_aliases`, `nim_tool_argument_aliases_from_body`, `clone_body_without_chat_template`, `clone_body_without_reasoning_content`, `clone_body_without_reasoning_budget`, and NIM request option helpers such as `_set_extra` and `build_nim_request_body`.

Shared Anthropic request serialization primitives should be reusable outside OpenAI conversion. In particular, serialization of Anthropic `tool_result.content` into provider-safe text should be available from `core.anthropic` as `serialize_tool_result_content` and should preserve the existing behavior: `None` becomes an empty string, strings are unchanged, dictionaries are JSON-serialized with `ensure_ascii=False`, lists are joined with newlines while text blocks contribute their `text`, other dictionaries are JSON-serialized, and other values are converted with `str()`.
